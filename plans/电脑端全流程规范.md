## 2. 统一后的五条主流程

### A. 云端代码审查 / 构建

```text
云端分支或本地已提交源码
  -> 固定完整 SHA、生成审查材料
  -> Linux 隔离快照、编译、测试、Lint、双包组装
  -> Windows 仅原签名与验签
  -> 本地 APK、哈希、来源和耗时回执
```

当前入口：`F:/eta/06-环境运维工具/eta-cloud-flow/eta-cloud-flow.ps1`。

已实施：公开源在 `/opt/eta/sources` 直接增量拉取；本地提交或需 Windows 凭据的私有源保留单次 `git archive` 通道。动态读取 APK 内实际 `versionName` 并要求包含完整来源 SHA，不再硬编码版本号。不要整体搬迁 `F:/eta`。

### B. 本地代码提交云端给别人协作

```text
隔离分支修改
  -> 只暂存明确文件并形成提交
  -> delivery 完整本地验证
  -> 推送对应开发分支（非 main/local）
  -> git ls-remote 读回同一 SHA
  -> 他人 fetch/pull 该开发分支
  -> 需要进入稳定个人版时，再开 PR 到 local
  -> 必需检查、审查和本人批准后合入
```

仅“给别人看或基于分支继续开发”时，推送开发分支即可，不必直接合入 `local`。代码推送与 APP Release 是两次独立授权；推送代码不自动发布 APK。

### C. 本地已构建 APP 快速发给其他设备（预览通道）

推荐 **GitHub Pre-release + Release 资产**，不要把 APK 提交进源码分支，也不要把短期 Actions Artifact 当长期下载页。

```text
精确源码提交已推送
  -> 本地 delivery 验证、Windows 原签名
  -> 新建非 v* 预览标签（避免误触稳定标签工作流）
  -> 创建 GitHub Pre-release
  -> 上传原签名 Release APK、SHA256SUMS、验证报告
  -> 云端读回资产并核对哈希
  -> 分享 Release 页面或 APK 直链给其他设备
```

预览通道适合本次已构建的热修复包，避免重新跑一遍云构建。其他设备用浏览器即可下载，下载后仍需核对哈希和证书，安装保持手动。

**当前 STGPT 修复包的状态**：精确提交、完整验证、开发分支推送和 Pre-release 均已完成，云端 APK 读回哈希一致。剩余仅是实际设备验收：`prompt_cache_key` 是路由提示而非命中保证，仍需同一旧会话验证 `cached_tokens`，并在第二台设备核对哈希、证书后手动安装。

### D. 正式稳定版发布（稳定通道）

```text
PR 合入 local
  -> 创建 v<versionName> 标签
  -> 现有 Eta Build 验证来源、跑 Lint/单测、构建并验签
  -> 自动创建 GitHub Release 草稿
  -> 维护者检查源码 SHA、包信息、证书、哈希和发布说明
  -> 手动发布草稿
  -> releases/latest 与 App 内更新检查可见
  -> 其他设备下载并手动安装
```

稳定标签必须属于 `local` 历史并匹配 `versionName`。预览通道不能冒充稳定版，也不能为了让更新检查可见而绕过草稿审核。

### E. 手机工程资料同步

继续独立于 Git 与 Release：仅按明确文件执行 `eta-phone` 拉取/写回，先处理现存同步锁并核验回执。手机资料同步不自动触发构建、代码推送、APP 发布或安装。

## 3. 电脑端统一入口建议

| 入口 | 责任 | 明确不做 |
|---|---|---|
| `eta-cloud-flow.ps1` | 拉取/读取提交、审查、Linux 构建、Windows 签名、生成回执 | 不提交、不推送、不发布、不安装 |
| 现有 `eta-auto-push.ps1` | 仅夜间白名单分支的提交后自动验证与推送 | 不扩展到其他仓或其他分支 |
| `eta-ai-delivery.ps1` | AI 任务级仅显式文件提交、精确提交完整验证、非强制推送和 SHA 读回 | 不自动 `add -A`、不直接推 `main/local`、不创建 Release；失败保留本地提交但不推送 |
| 规划中的 APP 发布入口 | 将已经验签的本地 APK 发布为预览或稳定 Release，并读回资产 | 不重新隐式构建、不推送源码、不自动安装 |
| 规划中的状态入口 | 一页显示分支/WIP、最近构建 SHA、云端分支 SHA、Release 与设备验收状态 | 不修改任何状态 |

代码推送和 APP 发布必须保持两个命令、两份授权、两份回执，避免“构建完成”被误解为“可以公开发布”。

## 4. 分阶段实施建议

1. **规范落地（本规划）**：确认五条流程、预览/稳定双通道和现状缺口，不写远端。
2. **源码入口优化**：实现 `/opt/eta/sources` Linux 原生镜像，消除 `/mnt/f` Git 热路径；用同一提交做冷/热基准。
3. **代码协作入口**：在现有夜间门禁之外，为其他明确开发分支提供手动推送与远端 SHA 读回；默认拒绝 `main/local`。
4. **APP 预览发布入口**：增加 Pre-release 创建、APK/哈希/报告上传、资产读回和第二设备下载校验。当前终端未检测到 `gh`，可选择 GitHub 网页发布，或在用户明确授权后配置 GitHub CLI。
5. **稳定发布验收**：沿现有 `v*` 工作流检查草稿生成、人工发布、`releases/latest` 和 App 更新检查，不改变 `local` 保护规则。
6. **设备验收**：至少一台第二设备下载 Release，核对 SHA-256、原证书、包名/versionName 后再手动安装和验证旧会话缓存。

## 5. 安全和发布约束

- APK、密钥库、密码、账号数据、手机备份和私有日志不得进入 Git 源码提交。Release 只上传公开可分发 APK、哈希和脱敏验证报告。
- 公开仓库的 Release 也是公开内容；若以后改私有仓库，下载权限和更新检查需另行评估。
- 不自动创建标签、Release、PR、合并或安装；这些均需当次明确授权。
- 不直接推 `main/local`，不强推，不关闭测试/Lint，不把 Artifacts 当长期 Release，不把 Debug 包用于覆盖现用原签名安装。
