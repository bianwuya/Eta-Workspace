# Eta 前端审美和效率门槛

## 谁负责
AI 负责提出方案、对照官方源码、组件映射、自动自审和修复；用户只负责**第一次实质视觉变更的批准**。AI 不得替用户批准。后续同样组件/布局/过渡合同的纯复用无需重复问；超出批准内容必须重新展示差异才可扩大范围。

## 分级，避免拖慢开发
- T0：无 UI 效果的逻辑维护 → 不做预览，按测试回归。
- T1：原组件的文案/设置项/不改变整体层级的增量 → 直接给同组件状态图，用户一次审查；若明确已有批准基准可直接复用。
- T2：新的页面/较明显布局变化/复杂弹窗 → 主页面 + 关键状态图（一般 2–4 张）、组件参考与一份动效合同，一次展示。
- T3：跨页、手势、页面入退场重构 → 优先 Compose Preview/Animation Preview 或实际交互原型与短录屏，确认后方可实施。

## 一次审核包（UI-REVIEW.md）
1. 需求是否仅改某个目标页？官方参考页/组件的真实源码位置是什么？
2. 视觉焦点：用户第一眼看到什么？为什么不是其他块？
3. 二级信息：什么需要突出，什么应该弱化？按钮、选项、长说明怎样分组？
4. 同屏模拟：正常、加载、失败、空态、选中/展开，展示与任务相关的状态，避免无意义枚举。
5. MIUIX+COUI 两主题及浅色/深色的最小矩阵（若本任务仅单主题且用户明确限定，则其他主题只做回归）。
6. 动画：进入/返回/弹窗/手势，三帧或短视频 + 取消/连续点击/键盘。
7. 对照：已批准官方或用户基准，标出变更区域；用户以「通过/修改局部/否决」一次回应。
8. 清楚标记预览载体：①真实 Compose Preview、②真实设备/模拟器录屏、③仅概念 HTML/示意图。③不能当成真实实现验证。

## 审美可测门槛（避免 GPT 主观装饰）
- 与官方同类页相比，对齐、版心、圆角、上下节奏、标题/正文/说明层级一致；视觉上不挤不空。
- 只出现一个主强调目标；提示/警告除外。删除“为了好看”叠加的高光/渐变/边框/大图标。
- 主次按钮清晰、设置项标签和解释不冲突；状态变化不会导致跳动或误触。
- 通常至少 48dp 可触控区域；按字体缩放保持可读，长文本换行/省略有合理策略。
- 键盘弹出/IME、系统栏/刘海、单手触达、最小手机/较宽屏、暗色/亮色、旋转/恢复不严重变形。
- 具体双主题不互串 token；未指定默认只用 Eta 官方主题默认色彩。
- 用户已明确认可的局部组件不再改变。任何整体换风格必须重新批准。

## 正式实施后的自动视觉回归
- 从真实 Compose 截图建立 golden 基准（只有经过用户认可才可更新 golden）。
- 复用当前构建系统已有测试路径；**先查 AGP**。最新 Android 文档指出独立 `com.android.compose.screenshot` 插件不再维护，AGP 9.5+ 可考虑 suites；不可在该工程仍为 AGP 9.4.1 时擅自升级整套构建。
- 截图对比必须在一致的尺寸/density/fontScale/主题下做，报告差异并区分抗锯齿环境误差与真实布局偏离。
- 动画验证要覆盖快速连续点、返回中断、缩放、键盘、旋转、暗色切换。编译、静态扫描、截图都通过也不等于实际手机交互验收通过。
- 回归失败只修偏离点，最多两轮自主修复后标记 BLOCKED 和截图差异；禁止动未授权页面或隐瞒差异。
