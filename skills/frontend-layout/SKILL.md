# Eta 持续前端设计 Skill（用户长期约束，2026-11-12）

## 核心：模型不是自由设计师
**官方 Eta 组件与现有成熟页面就是设计系统。** 默认复用，禁止“为了更好看”改变整体配色、圆角、字体、间距、手势、动效和导航。无相同组件时才增量扩展，样式来自紧邻且同主题、同用途的官方控件。用户认可的界面样板优先于模型的审美判断；对“设计更美观”的口头声明不视为验收。

## 两种开发路径：省时而不擅自开工
### A：纯功能/文案维护，无可见布局变化
仅修改行为、逻辑或文字且不改变布局层次、颜色、尺寸、导航、动效的，可按工程授权直接实施，运行相关布局回归；不得借机做美化。

### B：新增界面、显著修改布局/视觉/动画
执行强制 **DESIGN_REVIEW_GATED**：
- **研究**：只取目标页与最近 2–3 个相同类型的官方 UI/组件作真实参照，列“官方直接复用/缺口需扩展”；不漫游全仓，不反复从头研究。
- **轻量草案**：由 AI 一次提出明确的信息层级、布局、操作状态与组件映射，先自动检查内容优先级、空态、错误态、加载态、横屏/小屏、暗色/亮色、双主题。初稿要做自我修正，不让用户来发现明显的间距错、重心失衡、文字裁切。
- **可审预览**：给用户一份简短审核包，包含真实官方组件参照截图（若可获取）、主界面及关键状态预览、动画/手势分镜或 5–12 秒短录屏/动图、差异标注、未模拟的部分。**HTML / SVG 概念稿仅证明信息结构，不得称“与 Android 真机等价”**。尽可能用目标工程中的真实 Compose @Preview/Animation Preview；若当前环境不能渲染 Compose，必须明确标记模拟程度。
- **只问一次**：用户在这一版预览上选择“通过 / 修改部分 / 否决”；只修改否决部分，已有批准部分不再推倒重来。无有效明确批准时，不开始正式界面源码改造。
- **正式实施**：锁定批准版布局及动画契约，使用官方 Compose 组件实现；无须每个控件再问用户，已批准范围内的细节由代理自己迭代修复。
- **自动复核**：真实 UI 截图与已批准样板比较，目标界面状态、主题/比例、交互/过渡测试；明显偏离时代理自修并提供差异，不把“编译成功”当审美通过。影响布局/体验的超范围变化需二次批准。

## 视觉焦点判定规则（不能只说主观好看）
- 进入页面第一眼必须清楚：**所在页面是什么、最重要状态是什么、下一步主操作是什么**。每个屏幕最多一个主操作视觉焦点。状态错误/危险操作可成为优先焦点。
- 信息层级：页面标题 → 最重要状态/主卡片 → 当前任务直接操作 → 次要配置 → 帮助/说明。避免所有元素等视觉权重，避免彩虹色徽章、重复强调、装饰性大留白。
- 保持对齐、节奏、组内/组间间距与邻近官方页面一致；优先沿用主题文字层级/现有控件默认内边距，不盲套 8dp 网格覆盖官方规范。
- 设置项沿官方 PreferenceGroup + 原生 Switch/Dropdown/Slider/对话框；信息密集屏幕避免不必要卡片套卡片。触摸目标尽量至少 48dp，视觉图标可小但可触控区域需足够。长文案不靠整体缩小字体处理。
- 双主题 Miuix/COUI 和浅/深色均需验证；不得某一主题借用另一主题背景、按钮、圆角与动效；不写死自造颜色代替 LocalUiStyle/MiuixTheme/CouiTheme。
- 适配小屏、字体放大、输入法、系统栏、安全区、横屏/多窗口；触摸/点击顺序合理，支持 TalkBack 语义和可用性。

## 动画是设计合同的一部分
必须先定义状态机和过渡方式，复用官方动画、反馈与交互曲线。禁止只看静态首帧就批准复杂动画；对导航前进/返回、弹窗出现/关闭、展开/折叠、拖拽/缩放、成功/失败提示和中断恢复，必须说明：
- 初始态 → 过渡态 → 终态；
- 触发、持续节奏、是否可逆/可打断、动画期间可否交互、状态是否保留；
- 尽量复用官方 motion spec，不新造全局统一毫秒值；支持系统减少动画/适当弱化。
以 [动效规范](references/MOTION.md) 为真实细则。

## 效率控制
- 不为**第一次设计审核**先构建整个 APK；用 Compose Preview、官方组件截图、必要时结构 HTML；动画预览只做受影响转场。用户不必看多个小版本。
- 只生成 1 个推荐方案；只有关键交互明显存在两种方案且都满足官方风格时才给 2 个精简变体，不生成无价值的五套图。
- 除用户要求或真实 UI 结构跨页外，不修改其他页，不全局改主题/字体/导航，不新增与官方重复组件；不把所有页面改成统一卡片样式。
- 现有已批准视觉基准可直接沿用，只有与本次需求冲突的部分重新审批。
- 静态检查与 AI 自审是**候选门槛**，不能替代用户视觉批准、真实 Compose 截图和手势运行测试。

## 交付物合同
设计阶段：`UI-REVIEW.md`（功能范围、真实组件映射、风格依据、屏幕状态、动画分镜、截图/预览路径、差异、未覆盖、等待用户选择）。
批准阶段：`UI-APPROVAL.md`（用户批准的版本/具体区域/时间、尚未批准、hash 或文件引用、动画要求）。记录精确证据，未经用户批准不能写“APPROVED”。
实施阶段：`UI-VALIDATION.md`（Git SHA、真实截图、预览基准、视觉差异、动态手势与过渡验证、未测项、回退）。
使用专用任务目录保存，不把源代码放知识库。任何新任务首先复用已存在的审核资产与组件映射，不再要求用户重复强调审美。
