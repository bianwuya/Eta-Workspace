# 备份与迁移：按风险选择，不默认大搬家

## 先判断是哪种变更

- 仅知识/文档/脚本：不安装，不备份整个手机。
- 正常同签名APK更新：通常覆盖安装，按本次数据风险选一个可用备份。签名证书必须与当前安装兼容，不能只看版本号。
- 首次官方→自签/换签名/清数据：不可直接覆盖，才需要完整迁移。后续自签版本继续沿用同一release keystore，避免无谓重装。

## 三类东西不要混淆

1. Eta内置JSON：当前基线格式eta-backup/schema4，包含会话、消息、提供商/模型、记忆及代码支持的角色数据。官方3.4.0和682fbd3备份相关源码无差异，可通用。API-Key配置可能明文在文件里；不把文件公开。
2. 完整文件备份：App CE/DE数据、DB+WAL、Skills/配置/记忆、rootfs、真实需要保留的App外部目录、共享工作区与构建keystore。共享工作区及挂载源是不同物理目录，排除rootfs中的宿主bind mounts，避免递归备份全手机。
3. AndroidKeystore/系统授权：不是普通文件。卸载删除的OAuth/语音/网页/MCP加密密钥不能靠复制App目录保证恢复，可能重登/填写；Root、无障碍、默认助手等要按新身份核验。完整文件镜像不承诺“凭据和授权100%原样”。

## 真要换签名时的必要流程

1. 先检查实际包名/签名/版本、剩余空间和供电，保存原APK、目标APK及hash、一次可恢复备份。若电量/充电证据冲突才查dumpsys/sysfs。
2. 为当前Eta自迁移使用独立执行器：Android全局namespace，UID/父进程/cgroup/cwd/FD不依赖将卸载的App。先验证，再执行；不要仅靠睡眠/后台化就假定独立。
3. 备份需有可恢复的DB一致性；在线安全快照不是最终停机冷备。停止App和确属该rootfs的进程后完成冷副本，数据库integrity_check及归档/hash基本校验通过再卸载。无需把每一层又嵌多份递归快照。
4. 新安装读实际UID。只转换旧App所有权的文件/组；保留Debian root文件和各Linux用户原UID/GID。按原策略恢复SELinux，根环境标签与普通App数据MCS类别分别处理，不全盘chmod/chown。
5. 恢复后检查数据计数/记忆/Skills/工作区、Linux实际执行、安装身份，再检查Root/无障碍/模型连接/新功能。日志里的“已恢复文件”不代表所有权限/加密登录/OEM功能也验证。
6. 失败按失败阶段判断是否回滚，不能无脑再次卸载。保留原APK+已验证备份+日志；回滚也不能恢复卸载删除的KeyStore密钥。

## 保留与隐私

至少保留一个已验证可恢复快照和相配原/目标APK、长期release keystore。待新版本验收后再由用户决定清理大型中间副本，不默认永久无限保留，也不擅自删除唯一回滚材料。下载目录是用户可访问副本，不是保险柜；备份含聊天、API Key和签名私钥，不向远端/仓库上传。
